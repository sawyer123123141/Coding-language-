# Determinism, round 1: the same inputs give the same game (design, 2026-10-27)

## Why

The user chose "Determinism first" on 2026-10-27. The proposal (`docs/superpowers/plans/2026-10-27-determinism-proposal.md`, read it whole) gives the demand and what breaks determinism today: transcendental math goes through the Microsoft C runtime, which picks different code on CPUs with FMA3; exes target the build machine's CPU; nothing pins MXCSR; the only random generator is hidden and clock-seeded; which of two failing `par for` iterations reports depends on timing; and `ring[k] = g` leaks the old snapshot's buffers until exit. This round builds the proposal's "Round 1". The user accepted the recommended names; every other choice is the controller's under the user's delegation, written here as decided.

## Goals

- G1. **The promise (level b):** the same exe gives bit-identical results on any x86-64 Windows machine; `kestrel run` (the JIT) and an exe from the same compiler and source agree; a checked build and a `--release` build compute the same values unless the checked one stops (an overflow, or an `@assume` that is false and trusted under `--release`).
- G2. `@prove(deterministic)` states and checks that promise per function or loop, with chained plain-sentence errors.
- G3. Rollback state is cheap: a seeded `Rng` lives in the state, `checksum(x)` detects desyncs, and assigning a snapshot over an older one reuses its storage, so a ring of snapshots stops allocating.
- G4. Rollback Pong in one process over a simulated network that never desyncs, with a checked in-memory replay, and the same final checksum headless in the JIT, the checked exe and the `--release` exe.

## Non-goals (out of round 1)

Files, `to_bytes`/`from_bytes`, `first_difference`, `kestrel replay`, real networking, hot reload, `reduce`, fixed-point numbers, ARM; a `u64` type (see decision 8); marking natives of built-in modules as deterministic; pinning MXCSR inside the Godot add-on's calls; `@prove(no_alloc)` over snapshots that hold lists, maps or strings (decision 9).

## Anti-goals (failures even if they "work")

- Any program's output changing because of storage reuse. Reuse changes memory only; every existing program test keeps its exact output in every build.
- Two live places sharing a buffer after an assignment, a buffer written while it is being read (`a = a`, `a = a.child`, `for s in g.history { g = s }`), a write into read-only memory (string literals), a dropped owning value, or memory that outlives its arena.
- A map loop that doesn't notice its map was replaced, or a range-analysis fact about a list's length that survives an assignment over it.
- A math result that depends on the CPU: no runtime CPU dispatch that can change a result (the JIT's `libm` copy has one, for `fma`, which nothing here calls).
- A promise worded wider than what is tested. "Proven" covers the language rules, not compiler bugs; the cross-build test is the guard.
- A visible window in any test.

## The design (decisions)

1. **Written rules.** Kestrel floats are plain IEEE: no fused multiply-add, no reassociation, no fast-math, no "strict" flag (strict is the only mode); no optimization may change a float result (the design rule for level c). Already true; now written in the syntax spec and guarded by a test that compiles `a * b + c` and finds no `fma` in the Cranelift IR. NaNs are canonicalised only where bits are read (`checksum`). Also written: map order never depends on hashing; every `pure` function is deterministic; checksums (and later serialization) walk fields, never padding.

2. **Kestrel's own math.** `sin cos tan asin acos atan atan2 exp log pow` and the float remainder (`kestrel_rt_fmod_f32/f64`, today Rust's `%`, which calls the C runtime's `fmod`) call the `libm` crate, a pure-Rust port of musl's libm. It is already in `Cargo.lock` at 0.2.16 (through `cranelift-codegen`) and in the local registry, so nothing downloads. It is pinned `=0.2.16` with `default-features = false`: the `arch` feature only swaps in `sqrtsd` and a runtime-detected FMA for `fma` (which these functions don't call), so turning it off leaves no CPU detection in an exe's math. The JIT's copy of the runtime is built inside the compiler, where Cargo unifies features with `cranelift-codegen`'s own `libm` dependency and `arch` comes back on; that only changes `sqrt` (correctly rounded either way) and `fma` (which none of these functions call), so its results are identical, and the cross-build test (decision 12) pins JIT against exe bits for the whole table. Rust never contracts float operations, and `cli/build.rs` builds the runtime without `RUSTFLAGS`. `f32` operands still widen to `f64` and narrow once. A table of inputs per function (signed zeros, a subnormal, `1e22` for argument reduction, infinities, NaN, domain edges) pins exact result bits, each also within 1 ulp of today's `f64` functions, so the table is sane, not just frozen. `sqrt`, `floor`, `ceil`, `round`, `abs`, `min`, `max` stay IEEE-exact Cranelift instructions (with SSE4.1, `floor` and `ceil` are `roundsd`, never a libcall).

3. **MXCSR pinned** to `0x1F80` (round to nearest, every exception masked, no flush-to-zero, no denormals-are-zero) by a runtime function `fpu::pin()`: in `kestrel_rt_start` before `main` (the JIT goes through it too); when a pool thread joins a `par for` job, and when the caller thread does but only in a program started by `kestrel_rt_start` (a host such as the Godot add-on keeps its own thread's mode); and on return from every native of the window library (`window`, `draw`, `draw3d`, `input`), since a graphics driver may change it on the window's thread. Pinning costs one `ldmxcsr`, nothing measurable after a foreign call.

4. **Exes for a fixed baseline CPU.** `codegen/src/isa.rs` gets one `target_isa()`: x86-64 with Cranelift's `sse41` preset (SSE3, SSSE3, SSE4.1) and nothing else, from `cranelift_native::builder_with_options(false)`. `kestrel build` prints "built pong.exe for x86-64 CPUs with SSE4.1 (every one since about 2011)". An exe on a CPU without SSE4.1 stops at once with "this program needs a CPU with SSE4.1 (every x86-64 CPU since about 2011); this one doesn't have it". **The JIT uses the same ISA** (the controller's call). Host features would be safe for floats (Cranelift emits FMA only for an explicit `fma`, which Kestrel never emits, and AVX encodings compute the same IEEE operations), but one ISA means the JIT and an exe compile the same instructions from the same KIR, so a bug in a host-only lowering can't make them disagree. If measurement shows the JIT losing more than 2% anywhere, the host ISA can come back for it without touching the promise. On a host without SSE4.1 the JIT stops with the same sentence.

5. **`@prove(deterministic)`**, the fifth contract (`Contract::Deterministic`, `ContractSet::DETERMINISTIC = 16`). It holds when the result, and every change to `var` parameters, depends only on the arguments. It is decided on the events walk the other contracts use, followed through calls by the summaries. Three things break it, each a new event `What::Effect`:
   - **any native** (round 1 whitelists none: math is not a native and `print` is a statement), in words chosen by the native: `window.delta`, `window.time`, `window.ticks_usec`, `window.fps` "reads the clock"; `input.held`, `pressed`, `released` "reads the keyboard"; `input.mouse`, `wheel`, `mouse_delta` "reads the mouse"; any other "talks to the window, which a deterministic function can't depend on";
   - **the shared random generator**: `randf`, `randf_range`, `randi_range`, `rand_seed` (KIR `RandFloat`, `RandInt`, `Stmt::RandSeed`);
   - **a function value whose type isn't `pure`** (`KSig` gains `pure: bool`, set by lowering from the source signature) and **an interface method call** unless the interface method is `pure` or promises `deterministic`.
   `print` is allowed (a rollback re-runs it, so lines repeat). Maps, sorting and `par for` need nothing. Every `pure` function meets the contract, a written rule from now on. Messages, with their help lines:
   - "`step` can't be proven `deterministic`: it calls `window.delta` (line 14), which reads the clock"; help "pass the time step in as a parameter, like `step(var g, i, DT)`".
   - "`step` can't be proven `deterministic`: it calls `spawn_enemy` (line 30), which calls `randi_range` (line 8), which uses the program's shared random generator"; help "keep an `Rng` from the `random` module in the game state and call `g.rng.randi_range(1, 6)`".
   - "`update` can't be proven `deterministic`: it calls `input.held` (line 5), which reads the keyboard"; help "read input outside and pass it in an `Inputs` struct".
   - "`step` can't be proven `deterministic`: it calls the function value `on_hit` (line 21), which isn't `pure`"; help "give it a `pure` function type, like `pure (Fighter) -> int`".
   - An interface call: "... it calls a method of the interface value `s` (line 9), which isn't `pure` and doesn't promise `deterministic`"; help as today's `Help::Iface`.
   `@prove` on a native stays refused by the parser's existing message. The unknown-contract message lists five contracts.

6. **Snapshot-able `var` parameters**, a second check of the same contract with its own message, for function sites only: every `var` parameter (and `var self`) must have a type a snapshot can copy and checksum. One rule with `checksum` (decision 8): no `Arena`, no GPU object, no interface value, no function value, `pure` or not. "`step` can't be proven `deterministic`: its `var` parameter `w` holds an `Arena` (`w.mem`), which a snapshot can't copy and checksum"; help "keep arenas, textures, meshes, interface values and function values outside the state a deterministic function changes". The other kinds: "... holds a function value (`g.on_hit`), ..." and "... holds an interface value (`g.scene`), ...". (Cost of the one rule: a deterministic function can't take state holding a `pure` function value this round.) Lowering (`kir/src/lower/prove.rs`, which has the checker's tables and each parameter's `var` flag and source type) records the first offending path on the `ContractSite`; the contract check reports it. Generics need nothing extra: the checker already refuses owning and function types as a type argument (`check/src/generic/rules.rs`).

7. **The `random` module**, written in Kestrel (`driver/std/random.kes`): `pure`, no native, and no window library (`cli/src/main.rs` links that only for `window`, `draw`, `draw3d` and `input`).
   - `pub struct Rng { seed: i64 }`, made as `Rng(seed: 42)`. The field is the state: it starts as the seed and moves on with every draw, so it is snapshotted and checksummed with the game.
   - `pure next(var self) -> i64`: SplitMix64 with `+%`, `*%`, `^` and masked shifts (`>>` is arithmetic on `i64`, so `x >> 30` is followed by `& 0x3_FFFF_FFFF`), equal bit for bit to the reference for the same seed.
   - `pure randf(var self) -> float` in `[0, 1)` (top 53 bits scaled, narrowed to `float`, a result that rounds to 1 replaced by the largest `float` below 1, as the global does); `pure randf_range(var self, lo: float, hi: float) -> float`; `pure randi_range(var self, lo: int, hi: int) -> int`, both ends included, swapped when `lo > hi`, no overflow over the whole `int` range (the top 32 bits of a draw times the span, high half, in `i64` with wrapping operators).
   The global `randf` family stays for toys; the contract refuses it.

8. **`checksum(x) -> i64`**, a built-in, `pure`, no allocation, no failure. **It returns `i64`, not `u64`:** Kestrel has no `u64` type (only `int`, `i64`, `u8`), and adding one is syntax, the user's call; the 64 bits are the same, printed signed. It folds a value's contents in a fixed order, defined so a Rust reference can compute it:
   - start `h = 0x243F6A8885A308D3`; `mix(h, w) = x ^ (x >> 32)` where `x = (h ^ w) * 0x9E3779B97F4A7C15` (wrapping, unsigned shifts); the result is SplitMix64's finaliser of the last `h`;
   - a bool is 0 or 1; `u8`, `int`, `i64` are their value sign-extended to 64 bits; a `float` is its 32 bits zero-extended and an `f64` its 64 bits, every NaN replaced by the canonical quiet NaN (`0x7FC00000`, `0x7FF8000000000000`); `-0.0` and `0.0` differ (they are different values); a vector is its lanes in order;
   - a string is its byte length, then its bytes in 8-byte little-endian words (the last padded with zeros); an array or list is its length, then each item; a map is its live count, then each live key and value in insertion order; an optional is 0, or 1 then its payload; an enum is its variant number, then that variant's fields; a struct is its fields in order. Padding is never read.
   It is refused at compile time on a value holding an owning type ("`checksum` can't take a `World`, which holds an `Arena`; checksum the fields that hold the game's state instead"), a function value ("... which holds a function value, whose address differs between builds; ...") or an interface value ("... which holds an interface value; ..."; a hash slot in method tables is a later round). The algorithm may change between compiler versions until replay files pin it (round 2).

9. **Storage-reusing assignment** (no new syntax; Rust's `clone_from`). A plain `target = value` whose type holds a list, array, map or string but no owning value, and whose value reads an existing place, copies into the target's buffers when they have room:
   - Lowering calls a generated helper `__kestrel_assign_N(var dst: T, src: T)`, one per type like the copy helpers in `kir/src/lower/helpers.rs`; the value's place is found before the target's, as today.
   - **Lists and arrays:** room is `src.len <= dst.cap` for a list, `src.len <= dst.len` for an array (new KIR read `ExprKind::Cap`). With room, plain items move in one copy (new `Stmt::CopyItems`, which sets the length; range analysis treats it as a length write); items holding heap values are assigned recursively over `0 .. min(old len, new len)`, so inner buffers are reused, and copied fresh beyond the old length. **Without room it is exactly today's copy** (a fresh buffer in the current arena): reuse never grows a buffer, so arena placement is unchanged and the checker's escape rules stay sufficient.
   - **Strings** may be read-only literals, so a string is never written into: one whose bytes already equal the new value's is kept, any other is copied fresh.
   - **Maps:** an unlocked map with room takes a compact copy of the entries and index in place (runtime `kestrel_rt_map_copy_into`, `MapOp::CopyInto` returning whether it did); a locked map (being looped over) or one without room is copied fresh, so the loop still reports the replacement. Heap keys and values are copied fresh in round 1.
   - **Structs** go field by field; an **optional** or **enum** reuses its payload when both sides hold the same variant.
   - **Overlap falls back to today's copy.** After resolving loop-item pointers through lowering's `origins`, two places overlap when they have the same root and their paths overlap in the sense of the checker's `PathKey::overlaps` (one inside the other, any index matching any index), or when either root is a closure capture: `a = a`, `a = a.child`, `a.child = a`, `ring[i] = ring[j]`, `for s in g.history { g = s }`. Field-disjoint paths of one root don't overlap, so `p.ring[k] = p.game` reuses. Distinct roots can't overlap: every variable owns its data, and the exclusivity rule keeps `var` arguments apart (it still refuses `save(var p.ring, k, p.game)`).
   - **A target whose index expressions contain a call, or anything else that can write** (an assignment inside an `if`, a `var` argument), also falls back, so evaluation order and output stay exactly as today.
   - `let x = y`, fresh values (calls, literals), owning targets (`assign_owning`) and compound assignments are unchanged.
   **What `@prove(no_alloc)` proves:** save and restore of a snapshot type with no list, map or string (Pong's `Game`: numbers, vectors, an `Rng`, nested structs and enums) hold `no_alloc`, ring included. A snapshot holding a list keeps the fallback copy in its code, so `no_alloc` fails with a chain naming the assignment; the ring still stops allocating at run time (a test measures it), but a static proof needs a capacity fact range analysis doesn't have (round 2; any syntax for it is the user's call).

10. **A failing `par for` reports its lowest failing index.** Each participant records the start of the chunk it is running; a failure records (chunk start, message) and the smallest start wins. After the first failure no new chunk is taken; chunks already taken run to the end (chunks are handed out in increasing order, so every chunk below a failing one was already taken). A failing caller thread no longer exits at once: it waits for the other participants, then reports the winner. The same message wins with any `KESTREL_THREADS`.

11. **The demo**, `kestrel/demos/pong/`: two peers in one process, each with its own `Game` (ball, velocity, paddles, scores, `Rng`), stepped by `@prove(deterministic, no_alloc) pure step(var g: Game, i: Inputs)` at a fixed `DT = 1.0 / 60` (a headless window's clock is exactly 60 frames a second). A simulated network with its own `Rng` delays each packet 6 frames (100 ms) plus up to 2 frames of jitter and loses 5%; each packet carries the sender's last 8 inputs and its latest confirmed checksum. Each peer predicts the other's input (the last one received), keeps a ring of 16 snapshots, rolls back and re-runs to the present on a wrong guess, and waits a frame when it is 12 or more frames ahead of the other peer's newest known input. Peers compare checksums every 30 frames and stop with "peers differ at frame 1204". Player 1 is W/S or a bot when no key is held, player 2 a bot, so a headless run is scripted. Tab shows the other peer's view; R checks the in-memory replay (seed, confirmed inputs, a checksum every 60 frames). A headless run (`KESTREL_HEADLESS=600`, `KESTREL_HEADLESS_QUIET=1`) checks the replay at the end and prints `frames 600 confirmed <F> checksum <C>`, `checksums compared up to frame <K>` and `replay matches (<F> frames)`. A constant `DESYNC_AT` (-1) lets a test nudge peer 2's state and see the desync reported.

12. **The cross-build test** (`cli/tests/determinism.rs`): the `tests/programs/det_*.kes` programs and the demo run in the JIT, a checked exe and a `--release` exe, with identical standard output. `det_math.kes` prints every row of decision 2's table, so the JIT's runtime copy of `libm` (built with `arch` on) and the exes' copy (without) are pinned against each other bit for bit.

## Constraints

- No new syntax. New names: `deterministic`, the module `random` with `Rng` and its methods, the built-in `checksum`. The JIT/exe ISA change and the build line are behaviour, not syntax.
- Light mode for every build and test (`CARGO_BUILD_JOBS=2`, `--test-threads=2`, idle priority); **no build, test or benchmark while the user is gaming**: implementers wait until the controller says the PC is free. Never a visible window (`KESTREL_HEADLESS`, `KESTREL_HIDDEN` only); never a bare `link.exe`.
- Files under about 400 lines (`runtime/src/map.rs` is 494 already: the map copy goes in a new file); plain-sentence messages and comments.
- Never stage `kestrel/check/src/body/enums.rs`, `kestrel/test.kes`, `voxels.exe`; never edit `kestrel/bench/voxels3d/` sources.

## Tests

Names and assertions are in the plan. The ones that try to break storage reuse: overlap (`a = a`, `a = a.child`, `a.child = a`, `ring[i] = ring[j]`, a loop over the target's own history), same-root field-disjoint reuse (`p.ring[k] = p.game`), a target index with a call in it, lists of lists that shrink and grow, arrays, string literals, maps (including one being looped over), a source in an arena freed afterwards and a target in an `Arena` field (under `KESTREL_POISON=1`, with every arena dropped at exit), a `par for`, the checker still refusing a store out of `arena { }`, a killed length fact, and a snapshot ring whose program-arena bytes are equal after 2 and 200 periods. Every existing program test keeps its output. The whole suite and clippy at the end.

## Measurements (later, when the user says the PC is free)

In `kestrel/bench/determinism/results.md`, each with median, range and load: own math against today's per function; MXCSR pinning; baseline against host ISA on the frozen voxel world, `bench/kernels`, the engine bench's p99 and generation (exes and JIT); snapshot save and restore for Pong and a voxel-sized `Pool` (441 columns), with and without reuse; `checksum` on both.

## Left to the builder

How `fpu::pin` is written (inline `ldmxcsr` expected); whether `mix` and NaN canonicalisation are inline Cranelift code or runtime calls (decision 8 fixes the value); whether a struct's plain fields are assigned one by one or in byte runs; the internal shape of the `Effect` event and its summary chain, as long as the messages match decision 5.
