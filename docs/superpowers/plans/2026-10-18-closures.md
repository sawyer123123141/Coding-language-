# Closures and List Methods Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add function types, named functions as values, closure literals with by-value path captures, and the list methods `filter`, `map`, `any`, `all`, `sort`, `sort_by`.

**Architecture:** Each feature runs through `syntax → check → kir → codegen`.
- A function value is an aggregate `{code, env}`. Closure code is a KIR function that takes the environment pointer (an `I64`) first.
- The environment holds the captured values behind a 16-byte header (copy function, size). For a literal that is directly an argument of a user function, user method, function value or one of the five list methods, the environment is on the stack and holds shallow copies. Everywhere else it is in the current arena and holds deep copies.
- `filter`/`map`/`any`/`all` are helpers generated per call site that call a literal's code directly, so `inline_small` removes the call.
- `sort`/`sort_by` call a runtime stable sort with a less-than function generated per call site.

The templates:
- **Outlining:** `par for` (`check/src/body/par.rs`, `kir/src/lower/par.rs`, `codegen/src/func/par.rs`, `codegen/src/par_thunk.rs`, `func_addr` at `func/par.rs:23`).
- **Per-type helpers:** `has`/`find` (`kir/src/lower/list_helpers.rs`).
- **Scratch arenas:** natives (`kir/src/lower/call.rs` `scratch_parts`).
- **Memory tests:** `cli/tests/text_memory.rs` (two generated sources, compare the reports).

**Tech Stack:** Rust, Cranelift. Tests are Rust unit tests plus `.kes` program and error tests.

**Spec:** `docs/superpowers/specs/2026-10-18-closures-design.md`. Every message and behaviour below comes from it; the spec wins any conflict. The `@` spec (`2026-10-18-at-annotations-design.md`) is not built here.

## Review Focus

1. **A stack environment outliving its call.** Any store, return or copy of a stack-environment function value without a deep copy leaves a pointer into a dead frame. Defences:
   - only the checker's `Tables::stack_closures` decides which literals get one;
   - `kestrel_kir::check_stack_envs` runs after `lower` in debug builds and over every program test (Task 6);
   - the spec's `fs.add(...)` and `run(if c ...)` programs.
2. **Captured values sharing memory after a copy.** Cases: `let g = () { xs }` with two results changed separately; a copied closure; a closure capturing a closure. (Tasks 5 and 6.)
3. **A capture changed or freed during a call.** Every source of change in the exclusivity rule needs a test: var args, the `var self` receiver, the sort receiver, the callee place, sibling arguments, moves, and owning siblings. Views are followed to their source. (Task 6.)
4. **Memory growth in frame loops.** A literal passed to a function-typed parameter must allocate 0 bytes; `sort_by` with an allocating key must stay flat. (Tasks 6 and 8.)
5. **Parsing.** These stay unchanged: `if (ready) { }`, `in (w.mem) { }`, `while (x > 0) { }`, `match (e) { }`, `for v in (xs) { }`. A multi-line closure body inside call parentheses must parse. (Task 4.)
